| F-01 | High | Local | **PROP-LIFE-07 test method is factually incorrect.** The test method says "inject `AgentState` with non-empty `csp_decision` containing `cycle_pnl=930.00` and `cycle_annualised_return_pct=33.21`". `CspDecision` has no `cycle_pnl` or `cycle_annualised_return_pct` field — those live on `WheelPosition` and are emitted by `wheel_cycle_summary`. What `_build_options_context` actually reads from `csp_decision` is `mid_premium`, `delta`, `annualised_yield_pct`, `probability_of_profit`, `max_loss`, and `earnings_clear` (TSPEC §5.5). The property conflates two separate injection mechanisms: `_build_options_context` (which builds from `CspDecision`/`CcDecision` in `AgentState`) and `past_context` (which is populated from `TradingMemoryLog` and contains prior-cycle financials). The test as written will fail at fixture construction time because `CspDecision.model_validate_json` will reject a JSON blob with `cycle_pnl` as an unknown field (depending on Pydantic model config), or the assertion `assert "930.00" in result` will simply never be true because `_build_options_context` never emits that value. The property source and description are correct — the test method must be rewritten to: (a) use a `CspDecision` fixture with realistic field values (`mid_premium`, `probability_of_profit`, etc.) and assert those values appear in the context string; (b) test the "no prior cycle" path by passing `AgentState` with both `csp_decision=None` and `cc_decision=None`. | PROP-LIFE-07 |

The test method says "Compute `cycle_annualised_return_pct` for the canonical example" but does not specify which function to call. The formula is implemented in `wheel_cycle_summary` (TSPEC §6.3, step 4) — a LangGraph node function. | F-12 | Low | Local | **PROP-DATA-10 does not specify the test seam values for σ and T.** The test method says "Call with `_spot_price = _strike`, a reasonable σ, `option_type='put'`" without giving a specific σ or DTE. However, an extremely short-dated ATM put (T → 0) has Delta → -0.50 exactly, while a deep long-dated put has Delta → -0.50 also. ## Questions

| ID | Question |
|----|---------|
| Q-01 | PROP-LIFE-07 references "PLAN B3-T6 (past_context injection)" as the source for the `_build_options_context` property. Does B3-T6 intend to test the full options-context string injection (from `CspDecision`/`CcDecision` into debate prompts), or the `past_context` memory-log injection (from prior cycle `cycle_pnl`)? The TSPEC (§5.5) describes `_build_options_context` as reading only from `csp_decision`/`cc_decision`, not from memory log data. Clarifying this in the PLAN B3-T6 task description would prevent the test method confusion identified in F-01. |
| Q-02 | PROP-TRADE-10 and PROP-TRADE-13 test `annualised_yield_pct` and `strike_above_cost_basis` by direct `CspDecision`/`CcDecision` construction (not by running the agent). TSPEC §5.2 and §5.3 state these are "derived fields computed deterministically after LLM selects strike, never delegated to LLM." Does the TE intend for these to be pure schema-level construction tests, or should there be an additional property verifying the derivation runs correctly inside the agent (i.e., that the agent actually calls the derivation formulas and does not accept an LLM-provided value)? |
| Q-03 | PROP-LIFE-05 tests that `os.replace` failure leaves no `.tmp` file. After the mock raises `OSError`, the except clause calls `os.unlink(tmp_path)`. With `pytest tmp_path`, the directory still exists but the temp file should be deleted. However, if `os.unlink` itself raises (e.g., file already gone), the cleanup silently passes. Should the test explicitly confirm that `os.unlink` is called on failure, or just assert no `.tmp` files remain? The TSPEC §9.3 `except` block has `try: os.unlink(tmp_path); except OSError: pass` — so unlink failure is swallowed. The `tmp_path` assertion is the correct approach, but clarify whether the assertion is `assert len(list(tmp_path.glob("*.tmp"))) == 0` post-exception. |
| Q-04 | PROP-CONFIG-04 (P1, inline comments) specifies a test method of reading `default_config.py` and asserting a comment line adjacent to each key. This is a file-content assertion, not a behavioral assertion. Is this level of source-format enforcement appropriate as a pytest test? A linting check or a CI grep would be more conventional. Raising this as a question since P1 classification means it's "should-pass" but not blocking — if the team decides this is a documentation-quality check rather than a test, it could be removed without loss of behavioral coverage. |

## Positive Observations

- The three-layer fallback coverage (PROP-FALLBACK-01 through PROP-FALLBACK-13) is thorough and correctly cross-references ADR-WHEEL-04 for each scenario. The explicit `STRUCTURED_OUTPUT_SENTINEL` import requirement in the section note and in each individual test method is excellent — it prevents the most common sentinel-hardcoding mistake.
- BSM numerical anchors in PROP-DATA-08 and PROP-DATA-09 reference the specific injectable seam parameters (`_spot_price`, `_risk_free_rate`, `_sigma`) which are correctly specified in TSPEC §2.1.3. The canonical input values and expected outputs are reproducible and verifiable against the TSPEC §2.1.3 worked example.
- PROP-LIFE-04 (integer sort regression guard) and PROP-LIFE-05 (atomic write) are concrete and fully specify the `tmp_path` fixture use — exactly the isolation pattern required by ADR-WHEEL-05.
- The coverage matrix in §9 is complete and traceable. Every REQ and ADR entry has at least one PROP mapped to it. The known gaps in §10 are appropriately acknowledged with disposition notes.
- PROP-ROUTE-03 through PROP-ROUTE-06 are correctly classified as Unit tests (they call `route_wheel_phase` directly with a dict input, no graph invocation). This is the right granularity for routing logic.
- PROP-TRADE-11 (`_filter_csp_candidates` boundary test) is well-specified: it calls the deterministic filter function directly with explicit `abs(delta)` values at boundary, inside, and outside the target range. This tests the business-critical filter in isolation from the LLM.
- PROP-LIFE-08, PROP-LIFE-09, and PROP-LIFE-10 cover Rule 3 and Rule 4 boundary conditions directly against the deterministic rule-evaluation code path, correctly bypassing the LLM. The boundary values (`spot=85.0` vs `85.1`, `abs(delta)=0.10` vs `0.09`) match the FSPEC-WHEEL-06 edge-case specifications exactly.

## Recommendation

**Needs revision**

### Changes required before approval

**F-01 (High) — Must fix PROP-LIFE-07 test method:**
Replace the test method with: (a) inject `AgentState` with a valid `CspDecision` JSON string containing known values for `mid_premium`, `probability_of_profit`, `delta`, `max_loss`, `earnings_clear`; call `_build_options_context(state)`; assert the returned string contains those values. (b) For the "no prior cycle" path, inject `AgentState` with `csp_decision=None` and `cc_decision=None`; assert the returned string does not contain `"Past Cycle Performance"`. Remove all references to `cycle_pnl` and `cycle_annualised_return_pct` from the test method — those fields do not exist on `CspDecision`. The description of the property is correct; only the test method is wrong.

**F-02 (High) — Must fix PROP-DATA-08 Delta tolerance:**
Change `abs(delta - (-0.4602)) <= 0.001` to `abs(delta - (-0.4602)) <= 0.0005` to match TSPEC §2.1.3. Also update the source reference note in the test method.

**F-03 (High) — Must add missing `csp_open` guard property:**
Add `PROP-ROUTE-10`: When `wheel_phase="csp_open"` but no `WheelPosition` with `csp_strike` set exists for the ticker, `route_wheel_phase()` must raise `WheelStateError`. Test method mirrors PROP-ROUTE-08 but for the `"csp_open"` phase path.

**F-04 (Medium) — Must fix PROP-SCREEN-06 test method:**
Remove the "Inspect the factory function source or use `inspect.signature`" alternatives. The only valid test method is: mock `bind_structured` and assert it was called once with `(llm, WheelCandidateReport, "wheel_analyst")` as positional arguments.

**F-05 (Medium) — Must fix PROP-DATA-13 test precondition:**
Add an explicit precondition: set `config["wheel"]["risk_free_rate_source"] = "yfinance_irx"` (not `"static"`) before calling `get_options_greeks` with `_risk_free_rate=None`. This ensures the test exercises the `^IRX` fetch path and its fallback, not the static-rate shortcut.

**F-06 (Medium) — Must fix PROP-LIFE-03 test method:**
Specify which callable is invoked. Two acceptable resolutions: (a) if `wheel_cycle_summary` computes the formula inline without an extractable helper, the test method should inject a complete `AgentState` dict with a `WheelPosition` fixture (via `tmp_path`) containing `cycle_pnl=930`, `csp_strike=140`, `shares_held=100`, `csp_open_date`, and `call_away_date` (73 days later) and call `wheel_cycle_summary(state, config)`; (b) if the TSPEC is updated to expose a standalone formula helper (e.g., `compute_cycle_annualised_return`), the test method calls that helper directly.

**F-07 (Medium) — Must fix PROP-FALLBACK-13 test method:**
Specify this as a pytest test using `ast.parse` + `ast.walk`. The test should open the source files of each of the four wheel agent modules and `structured.py`, walk all `ast.Constant` nodes, and assert that the sentinel string literal appears only in `structured.py` (in the constant definition) and nowhere else. This makes the sentinel-enforcement property a real automated test rather than a documentation note.

**F-08 (Medium) — Must add PROP-LIFE-12:**
Add `PROP-LIFE-12`: `prior_analyst_bias` persistence across sequential `RollCheckAgent` invocations. The property should verify that after `RollCheckAgent` runs and writes an updated `WheelPosition` with `prior_analyst_bias = "bullish"`, a second invocation of `RollCheckAgent` reads `prior_analyst_bias = "bullish"` from the loaded position. The test must use `tmp_path` for I/O isolation and inject `_position_loader` to bypass the filesystem in the agent itself while using `save_wheel_position` / `load_latest_open_position` for the I/O-layer round-trip verification. This is mandated by TSPEC §9.1 ("PROPERTIES tests must cover this field") and ADR-WHEEL-05 Consequences.
